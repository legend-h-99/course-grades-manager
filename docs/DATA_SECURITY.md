# ضوابط أمن وخصوصية بيانات سند

تاريخ المراجعة: 5 سبتمبر 2026. هذه وثيقة تشغيل وضوابط تقنية، وليست شهادة امتثال أو ضمانًا بعدم وقوع اختراق.

## الضوابط المطبقة

- تصنيف الأسماء والأرقام الوظيفية والتدريبية والدرجات وملفات الحساب كبيانات شخصية مقيدة. تقتصر المعالجة على إدارة المقررات والدرجات.
- الملف الشخصي لصاحبه؛ بيانات المقرر لأعضائه؛ إدارة بيانات المقرر وملكيته للمالك. المستخدم لا يستطيع إضافة نفسه لمقرر آخر عبر REST، ويجب المرور بدعوة صالحة.
- منع أدوار العملاء من TRUNCATE وTRIGGER وREFERENCES، وسحب الوصول المجهول لجداول التطبيق. سجل الأمن ومحاولات الدعوات غير قابلين للقراءة المباشرة من المستخدمين.
- دوال SECURITY DEFINER الضرورية محددة الصلاحيات وتتحقق من المستخدم أو العضوية، وتبقى تحذيرات المستشار لهذه الدوال متوقعة وتحتاج مراجعة عند تعديلها.
- حماية كلمات المرور المسرّبة مفعّلة لدى Supabase. تأكيد البريد مفعّل والدخول المجهول معطّل. لا تحفظ المنصة كلمات المرور في ملفاتها أو سجل الأمن.
- جلسة المتصفح مشفرة، ومفتاحها غير قابل للتصدير في IndexedDB. هذا لا يمنع JavaScript خبيثًا من استخدام جلسة نشطة؛ لذلك تبقى حماية XSS وCSP ضرورية.
- حقول الملف الشخصي المؤسسية واسم المدرب ورقمه فيه، وأسماء المتدربين وأرقامهم تشفر عبر خادم التطبيق. رفض الحفظ إذا غاب مفتاح التشفير أو تعذر تحميله. بعض الحقول الأخرى وبيانات Auth ليست مشفرة بهذا التشفير التطبيقي. الوصول المباشر المصرّح به إلى REST لا يمر بتشفير Worker.
- حماية HTTPS وCSP ومنع تضمين الصفحات ومنع إرسال Referrer. ردود API لا تخزن مؤقتًا، ولا تعيد نصوص أخطاء قاعدة البيانات الخام.
- قبول طرق HTTP المحددة وJSON فقط للطلبات المعدّلة، مع حد فعلي 2 MiB حتى دون Content-Length، ورفض مصادر المتصفح الخارجية.
- سجل قاعدة البيانات يسجل معرّف الفاعل ونوع العملية والجدول والوقت فقط، دون نسخ الأسماء أو الدرجات أو كلمات المرور أو رموز الجلسات. يبدأ من تاريخ تفعيله ولا يعيد إنشاء التاريخ السابق.
- دالة إنشاء مستخدمي الاختبار في الإنتاج معطلة وظيفيًا وتطلب JWT.

## قواعد التشغيل والتطوير

1. يمنح المسؤول أقل صلاحية لازمة، ويستخدم حسابًا شخصيًا بدل الحسابات المشتركة؛ تزال صلاحيات المغادرين فورًا.
2. يجب استخدام MFA لحسابات الإدارة في Supabase وCloudflare وGitHub. لم يُتحقق في هذه المهمة من تفعيل MFA لهذه الحسابات، ولا من إمكانية فرضه للمستخدمين داخل التطبيق.
3. لا توضع أسرار الخادم في Git أو ملفات الواجهة أو التقارير أو المحادثات. تحفظ في مخزن أسرار المنصة. عند انكشاف سر يُقيّم نطاقه ويُدوّر مع اختبار الاسترجاع؛ لا يُدوّر مفتاح تشفير الحقول دون خطة إعادة تشفير.
4. تستخدم بيانات اصطناعية في الاختبارات. اختبارات SQL هنا تنفذ في معاملة تنتهي بـ ROLLBACK ولا تترك حسابات أو درجات اختبار.
5. قبل النشر: npm test ثم npm run test:security ثم git diff --check. تشغل اختبارات supabase/tests/data_security.sql بعد تغييرات الصلاحيات.
6. تراجع تنبيهات الأمان بعد migrations، وتعالج الثغرات حسب أثرها. لا يحذف فهرس لمجرد عدم ظهور استخدامه خلال فترة قصيرة.
7. يمنع تضمين محتوى الصفوف أو كلمات المرور أو الترويسات السرية في السجلات. يراجع الوصول إلى السجلات دوريًا.
8. الملفات التي يصدرها مستخدم مخول تتضمن بيانات المقرر؛ يجب حفظها على أجهزة ومساحات تخزين معتمدة وعدم إرسالها لمستلمين غير مخولين. لا يمكن لهذه التعديلات منع تصوير الشاشة أو إعادة مشاركة الملفات بواسطة مستخدم مخول.

## الاستجابة للحوادث

- يبدأ المسؤول بسجل زمني للحادثة ونطاق البيانات المحتمل تأثرها، ويحفظ الأدلة في مساحة مقيدة دون نسخ بيانات حساسة في قنوات عامة.
- يحتوى المسار المتأثر بأقل تعطيل ممكن، ثم تلغى الجلسات أو تدور الأسرار المتأثرة عند الحاجة، مع الحفاظ على القدرة على التحقيق والاسترجاع.
- يقيم مسؤول الخصوصية شروط إشعار الجهة المختصة خلال 72 ساعة من العلم عند انطباق المادة 24 من اللائحة التنفيذية، وإشعار أصحاب البيانات بحسب المتطلبات المنطبقة. لا يؤخر التقييم انتظار اكتمال التحقيق.
- يوثق السبب والإصلاح ويختبر منع تكراره، وتراجع الصلاحيات وخطة الاسترجاع.
- المصدر: https://dgp.sdaia.gov.sa/wps/portal/pdp/services/personaldatabreachnotification

## متطلبات متبقية قبل تأكيد الامتثال

- تحديد جهة التحكم بالاسم، مسؤول الخصوصية ومسؤول الحوادث، والتحقق من عمل بريد الدعم ومسار طلبات الوصول والتصحيح والحذف.
- اعتماد مدد الاحتفاظ لكل فئة بيانات وتنفيذ الحذف الدوري مع مراعاة الاحتفاظ القانوني والنسخ الاحتياطية. لم ينفذ حذف تلقائي أو حذف بيانات موجودة في هذه المهمة.
- التحقق من النسخ الاحتياطية وPITR وتجربة الاستعادة واعتماد RPO/RTO؛ وجود الاستضافة وحده لا يثبت الاسترجاع.
- تقييم نقل البيانات واتفاقيات المعالجة: قاعدة Supabase الحالية ap-south-1، وSmart Placement لا يضمن إقامة المعالجة في السعودية أو الشرق الأوسط. لا توجد شهادة امتثال PDPL/NCA ضمن هذه المهمة.
- تقييم الحاجة إلى ضوابط NCA الخاصة بالجهة، وتوثيق المطابقة بندًا بندًا بعد تحديد نطاقها التنظيمي.
- إعداد تنبيهات تشغيلية أمنية ومسؤول يتلقاها، وتحديد معدل الطلبات على مستوى موزع. المحدد الحالي داخل Worker محلي لكل isolate وليس حدًا عالميًا مضمونًا.
- مراجعة الحقول النصية القديمة وآلية ترحيلها إلى تشفير موحد عند الحاجة؛ لا ندعي أن كل صف قديم أو عمود مخزن مشفر بالتشفير التطبيقي.
- تعالج الفواتير المستحقة الظاهرة في لوحة Supabase بواسطة صاحب الحساب لتجنب تعطيل الخدمة؛ لم يُجرَ أي دفع.
